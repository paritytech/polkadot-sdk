# Plan: Deprecating `RuntimeVersion` for JAM runtimes

## 1. Goal

Parachains running on JAM (via the parachain service) should stop using `RuntimeVersion` as the
source of truth about a runtime:

- **A runtime is identified by its code hash.** Node and runtime use it to tell runtimes apart
  and to detect upgrades.
- **The node reads everything it needs from the runtime blob**, without executing it:
  - the runtime APIs and their versions,
  - the consensus-relevant system features (state version, ...).
- **`RuntimeVersion` / `Core::version` only stay for backwards compatibility** with UIs and
  wallets (Polkadot-JS, PAPI). Only `spec_version` remains meaningful.

## 2. Background

### 2.1 What `RuntimeVersion` contains

| Field | Used for |
|---|---|
| `spec_name` | Upgrade detection (`LastRuntimeUpgrade`), `can_set_code`, Polkadot-JS type selection, code overrides |
| `spec_version` | Upgrade detection, `CheckSpecVersion`, Polkadot-JS metadata caching, RFC-78 metadata hash, code overrides / substitutes |
| `transaction_version` | `CheckTxVersion` |
| `impl_name`, `impl_version`, `authoring_version` | Effectively unused |
| `apis` | Node: `has_api` / `api_version`. Polkadot-JS: checks that the `Metadata` API exists |
| `system_version` | Consensus: trie state version, extrinsics root version, `:pending_code` usage |

### 2.2 Runtime side consumers

- **Upgrade detection:** `frame-executive` (`runtime_upgraded()`) compares `spec_name` /
  `spec_version` with `frame_system::LastRuntimeUpgrade` (`substrate/frame/system/src/lib.rs:1267`).
- **`can_set_code`** checks `spec_name` / `spec_version` of the new code. Not possible on JAM:
  upgrades only provide the code hash.
- **`CheckSpecVersion` / `CheckTxVersion`** add `spec_version` / `transaction_version` to the
  signed payload.
- **`system_version`** decides whether `set_code` writes to `:code` or `:pending_code`
  (`substrate/frame/system/src/lib.rs:1596`, `validate_block_core.rs:255`).

### 2.3 Node side consumers

- **State version (consensus critical):** derived from `system_version` when executing blocks
  (`substrate/client/service/src/client/call_executor.rs`). The extrinsics root version is derived
  from it when building blocks (`substrate/client/block-builder/src/lib.rs:333`).
- **Runtime API discovery:** `has_api` / `api_version`, used by aura, babe, the transaction pool,
  offchain workers, the block builder, the cumulus collator and more.
- **Code overrides & substitutes:** keyed by `spec_name` / `spec_version`
  (`substrate/client/service/src/client/{code_provider,wasm_override,wasm_substitutes}.rs`).
- **RPC:** `state_getRuntimeVersion`, `state_subscribeRuntimeVersion` and the `newRuntime` event
  of `chainHead_v1_follow`.

### 2.4 Clients

**PAPI (polkadot-api v2):**

- Identifies runtimes by the hash of `:code` and caches metadata per code hash. Never calls
  `Core_version`.
- Fetches the code hash on every `newRuntime` event of `chainHead_v1_follow`.
- Discovers runtime APIs from the metadata (v15+), not from `RuntimeVersion.apis`.
- Signs with `spec_version` / `transaction_version` from the **`System::Version` metadata
  constant**. It must exist and be a struct.

**Polkadot-JS (`@polkadot/api` v17):**

- Gets the version only via `state_getRuntimeVersion` / `state_subscribeRuntimeVersion`.
- Reloads metadata **only when `specVersion` changes** (equality check). If it stays the same
  across an upgrade, the old metadata is silently kept.
- Caches metadata by `genesisHash + specVersion` and `specName + specVersion`.
- Uses `apis` to check for the `Metadata` API (version >= 2), otherwise falls back to v14
  metadata.
- Signs with `specVersion` / `transactionVersion` from the RPC.

**Ledger:** no longer uses `transaction_version`.

## 3. Decisions

### 3.1 `RuntimeVersion` becomes a compatibility shim

Only `spec_version` is set by the developer and must be increased on every upgrade. All other
fields get defaults:

| Field | Value |
|---|---|
| `spec_name`, `impl_name` | Package name of the runtime crate (`CARGO_PKG_NAME`) |
| `spec_version` | Set by the developer |
| `impl_version`, `authoring_version`, `transaction_version` | `0` |
| `apis` | `RUNTIME_API_VERSIONS` |
| `system_version` | Latest legacy value (§3.3) |

`spec_version` has to stay because:

- Polkadot-JS only reloads metadata when it changes (§2.4).
- Both clients sign with it, so transactions signed for an old runtime are rejected.
- The RFC-78 metadata hash contains it.

### 3.2 `Core::version` is generated by `impl_runtime_apis!`

The `Core` implementation gets a `#[spec_version(N)]` attribute:

```rust
impl_runtime_apis! {
	#[spec_version(7)]
	impl sp_api::Core<Block> for Runtime {
		fn execute_block(block: <Block as BlockT>::LazyBlock) {
			Executive::execute_block(block)
		}

		fn initialize_block(header: &<Block as BlockT>::Header) -> ExtrinsicInclusionMode {
			Executive::initialize_block(header)
		}
	}
}
```

- With the attribute, the macro generates `fn version()`.
- A manual `fn version()` without the attribute emits a **deprecation warning**
  (`proc-macro-warning`).
- Both together are a compile error.
- `execute_block` / `initialize_block` stay manual, as they depend on `Executive`.

The macro also generates:

- `pub const RUNTIME_VERSION: RuntimeVersion`, used as `frame_system::Config::Version`
  (`CheckSpecVersion`, `System::Version` metadata constant).
- The `runtime_version` custom section.

### 3.3 `system_version` becomes `SystemFeatures`

`system_version` bundles independent features into one number. It is replaced by a bit vector:

```rust
#[derive(Encode, Decode)]
pub struct SystemFeatures(BitVec<u8, Lsb0>);

impl SystemFeatures {
	pub const STATE_V1: usize = 0;
	pub const EXTRINSICS_ROOT_V1: usize = 1;
}
```

The `system_features` section contains the SCALE encoded `SystemFeatures`.

| Legacy `system_version` | Meaning | Bits set |
|---|---|---|
| 0 | State V0, extrinsics root V0 | none |
| 1 | State V1 | `0` |
| 2 | + Extrinsics root V1 | `0, 1` |
| 3 | + Delayed upgrades via `:pending_code` | `0, 1` |

- `:pending_code` gets no bit: on JAM, delayed upgrades are the default (`pallet-jam-system`
  upgrades by hash via `PendingCodeHash`).
- Unknown bits are ignored by the node.
- The legacy `u8` stays in `RuntimeVersion`. The node only falls back to it for runtimes without
  a `system_features` section.

### 3.4 Runtime APIs and `SystemFeatures` are custom sections

Both are emitted as `#[link_section]` statics and read by the node without executing the
runtime:

- **`runtime_apis`:** generated by `impl_runtime_apis!`. Stores the full name of each runtime API
  with its version, instead of the `ApiId` hash.
- **`system_features`:** new (§3.3).

The PVM blob format supports custom sections, the tooling does not yet:

- Section ids `>= 128` are optional and skipped by parsers that do not know them.
- `ProgramBlobBuilder::add_custom_section` already exists (used for debug info).
- **Missing:** `polkavm-linker` cannot turn an ELF section into a custom blob section. Unknown
  sections end up as read-only data, so today `runtime_apis` is dead bytes in program memory.
- **Missing:** `ProgramParts` does not expose unknown optional sections, and
  `RuntimeBlob::custom_section_contents` does not support PVM blobs.

This is fixed upstream in PolkaVM (§4.1).

### 3.5 Upgrade detection by code hash

`pallet-jam-system` stores a `CurrentCodeHash`, set at genesis and updated when the pending
upgrade is applied (`cumulus/jam/pallet-jam-system/src/upgrade.rs`).

Upgrade detection (migrations / `on_runtime_upgrade`) compares against it instead of
`LastRuntimeUpgrade`.

### 3.6 `CheckCodeHash` transaction extension

A new `CheckCodeHash` transaction extension adds the code hash to the signed payload.

### 3.7 `chainHead_v1_follow`

The `newRuntime` event carries most of `RuntimeVersion`, as mandated by the JSON-RPC spec. Until
the spec changes, it is filled from the compatibility `RuntimeVersion`.

The spec should be changed to carry the code hash instead. Clients get everything else (runtime
APIs, `System::Version`) from the metadata.

## 4. Work items

### 4.1 Upstream: PolkaVM

- `polkavm-linker`: copy ELF sections with a well-known prefix (e.g. `.polkavm_custom.<id>`) into
  optional blob sections.
- Reserve section ids for `runtime_apis` and `system_features`, or one generic "named custom
  section" id.
- `polkavm-common`: expose custom sections when parsing a blob.

### 4.2 Upstream: JSON-RPC spec

- `newRuntime` event of `chainHead_v1_follow` carries the code hash instead of the runtime
  version. Then update `rpc-spec-v2`.

### 4.3 Primitives & macros

- `sp-version`: `SystemFeatures`, conversion from legacy `system_version`, `system_features`
  section.
- `sp-api` (`impl_runtime_apis!`):
  - `#[spec_version(N)]` with generated `fn version()`,
  - `RUNTIME_VERSION` const and `runtime_version` section,
  - deprecation warning for a manual `fn version()`,
  - full runtime API names in the `runtime_apis` section.

### 4.4 Node

- `sc-executor`: read `runtime_apis` and `system_features` from PVM blobs
  (`RuntimeBlob::custom_section_contents`).
- `call_executor.rs` / `block-builder`: state and extrinsics root version from `SystemFeatures`,
  falling back to legacy `system_version`.
- `rpc-spec-v2`: detect runtime changes in `chainHead_v1_follow` by code hash.
- Optional: key code overrides / substitutes by code hash.

### 4.5 Runtime / pallets

- `pallet-jam-system`: `CurrentCodeHash`, set at genesis and on upgrade.
- `CheckCodeHash` transaction extension.
- Upgrade detection for JAM runtimes based on `CurrentCodeHash`.
- JAM runtimes switch to `#[spec_version(N)]`.

## 5. Open points

- **Deprecation warning rollout:** ~35 runtimes in this repository implement `fn version()`
  manually. Migrate all together with the macro change, or introduce the warning gradually.
- **Section ids** have to be agreed on with the PolkaVM maintainers.
